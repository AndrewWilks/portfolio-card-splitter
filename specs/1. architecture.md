# Portfolio Card Splitter - Architecture Documentation

## Overview

Portfolio Card Splitter helps two or more people share a credit card cleanly, assign each charge, park money elsewhere while the card is interest-free, then settle with zero guesswork. This document describes the system architecture following Clean Architecture principles with a mobile-first design.

## Technology Stack

### Backend

- **Runtime**: Deno 2.5.x (JavaScript/TypeScript runtime)
- **Web Framework**: Hono (lightweight web framework for APIs)
- **Database**: PostgreSQL
- **ORM**: Drizzle ORM (type-safe SQL query builder)
- **Validation**: Zod (TypeScript-first schema validation)
- **Testing**: Deno's built-in test runner

### Frontend

- **Framework**: React with TypeScript
- **Build Tool**: Vite
- **Styling**: CSS modules with Tailwind CSS

### Development Tools

- **Version Control**: Git with GitHub
- **CI/CD**: GitHub Actions
- **Code Quality**: ESLint, Prettier
- **Containerization**: Docker (planned)

## Architecture Principles

The system follows **Clean Architecture** principles with clear separation of concerns:

1. **Shared Layer**: Domain entities, types, utilities, and validation schemas used by both frontend and backend
2. **Backend**: Repositories (data access), Services (business logic), Routes (HTTP API), Middleware (auth, validation, errors)
3. **Frontend**: Components (UI), Repositories (API client), Services (client-side logic)

### Dependency Direction

```text
Backend:  Routes → Services → Repositories → Database
             ↓         ↓           ↓
          Shared ← Shared ←───── Shared (Entities, Types, Utilities)

Frontend: Components → Services → Repositories (API calls)
             ↓            ↓            ↓
          Shared ←──── Shared ←───── Shared (Entities, Types, Utilities)
```

**Key Principle**: Repositories are NOT shared - backend repositories talk to the database, frontend repositories talk to the API. Only entities, types, and utilities live in the shared layer to avoid duplication.

## Core Domain Model

### Shared Entities (in `/shared/entities`)

Entities are rich domain objects with validation, business rules, and factory methods. They live in the shared layer and are used by both frontend and backend.

#### User & Access

- **User**: Email, password hash, first name, last name, role (admin/user), isActive
- **Session**: User authentication session with expiration
- **InviteToken**: Time-limited token for member invitations
- **PasswordResetToken**: Time-limited token for password resets

#### Financial Accounts

- **CardAccount**: Credit card account (issuer, name, last4, billing cycle, credit limit, owner)
  - Every Transaction belongs to exactly one CardAccount
  - Outstanding balance calculated per CardAccount: Sum(Transactions) - Sum(Payments)
  - Supports soft delete via `isActive` flag
  - Used for dashboard summaries and statement reconciliation
- **Card**: Optional physical/virtual card within an account (linked to Member for "who swiped")
  - Multiple Cards can belong to one CardAccount
  - Used for attribution in shared household scenarios
  - Does NOT affect splits or payments (tracking only)
  - Optional `memberId` field links to who typically uses the card
- **Pot**: Where money is parked (savings, loan offset, cash, etc.) with balance tracking
  - Supports SOLO (owner-only) and SHARED (ACL-based) visibility
  - Derived values: `reservedCents`, `availableCents` (not persisted)

#### Transactions & Allocations

- **Merchant**: Where transactions occur (name, location, merged status)
- **Tag**: Categorization with color coding
- **Transaction**: A charge or income (merchant, amount, date, **CardAccount** (required), **Card** (optional), allocations)
  - **Breaking Change**: All transactions now require `cardAccountId` (no default)
  - Optional `cardId` for attribution (must belong to same CardAccount)
  - Allocations must sum to exactly transaction amount (100% split)
  - Cannot mix percentage and fixed-amount allocations in same transaction
- **Allocation**: How a transaction is split among members (fixed amount or basis points)
  - XOR constraint: EITHER `basisPoints` (percentage) OR `amountCents` (fixed), never both
  - Rule-based validation enforced in entity and service layers
  - Each Member's share tracked separately

#### Reservations & Payments

- **Reservation**: Money reserved from a Pot against a Member's allocation
  - Links Pots → Allocations → Transactions (envelope budgeting workflow)
  - `allocationId` and `memberId` fields enable proper tracking
  - Cannot reserve more than Pot's available balance
  - Cannot reserve more than Allocation amount
  - Multiple Reservations can cover one Allocation (e.g., from different Pots)
- **Payment**: Actual payment from a Pot to a Transaction (reduces outstanding balance)
  - Required fields: `potId`, `transactionId`, `amountCents`, `paidOn`
  - Optional `reservationId` links to planned reservation
  - `needsReconciliation` auto-flagged when Payment ≠ Reservations
  - Reduces CardAccount outstanding balance: Transactions - Payments
- **Transfer**: Money movement between Pots or between Pot and cash

#### People

- **Member**: Person participating in shared expenses (name, email, role)

### Entity Patterns

All entities follow these patterns:

```typescript

  protected _id: string;
  protected _createdAt: Date;
  protected _updatedAt: Date;

  get id(): string;
  get createdAt(): Date;
  get updatedAt(): Date;
}

// Example: Transaction entity
class Transaction extends Entity {
  private _merchantId: string;
  private _amountCents: Cents;
  // ... other fields

  // Factory for new entities
  static create(data: CreateData): Transaction;

  // Reconstruct from database
  static parse(data: unknown): Transaction;

  // Validation schema
  static get schema(): ZodSchema;

  // Serialize for API
  get toJSON(): TransactionData;

```

### Key Entity Features

**Allocation** enforces business rules:

- If rule is `basisPoints`, must provide basisPoints (not amountCents)
- If rule is `fixed_amount`, must provide amountCents (not basisPoints)
- Cannot provide both; validation enforced in constructor and Zod schema

**Pot** computes derived values:

- `withDerivedValues(reservations)` - sets cached reserved/available amounts
- `get availableCents` - returns available balance (not persisted)
- `get reservedCents` - returns reserved amount (not persisted)

**Transfer** supports cash transactions:

- Either `fromPotId` or `toPotId` can be null (but not both)
- `isCashOut()`, `isCashIn()`, `isPotTransfer()` helpers

**Token & Session** prevent reuse:

- `isExpired()`, `isUsed()`, `isValid()` checks
- `use()` marks as used (idempotent)
- Private guards prevent manual misuse

### Backend Routes

HTTP API routes handle requests, validate input, and return responses. They live in `/backend/routes/{domain}`.

**Pattern**: Thin controllers that delegate to services.

```typescript

  app.post("/api/transactions", async (c) => {
    const body = await c.req.json();
    const transaction = await service.createTransaction(body);
    return c.json({ transaction: transaction.toJSON() }, 201);
```

**Route structure**:

- `/api/auth` - Login, logout, invite, password reset
- `/api/transactions` - CRUD for transactions and allocations
- `/api/pots` - CRUD for pots, reservations
- `/api/payments` - Record payments
- `/api/transfers` - Transfer between pots
- `/api/merchants` - Merchant and tag management
- `/api/people` - Member roster
- `/api/ledger` - Balances and settlement

### Frontend Repositories (NOT in shared)

Frontend repositories are API clients that fetch data from the backend. They live in `/frontend/repositories`.

**Pattern**: Thin wrappers around fetch/axios.

```typescript
// Example: TransactionRepository (frontend)
class TransactionRepository {
  async list(filters?: TransactionFilters): Promise<Transaction[]> {
    const res = await fetch(
      "/api/transactions?" + new URLSearchParams(filters)
    );
    const data = await res.json();
    return data.transactions.map(Transaction.parse);
  }

  async create(request: CreateTransactionRequest): Promise<Transaction> {
    const res = await fetch("/api/transactions", {
      method: "POST",
      body: JSON.stringify(request),
    });
    const data = await res.json();
    return Transaction.parse(data.transaction);
  }
}
```

## Database Schema (Simplified Overview)

The full schema is managed via Drizzle ORM in `/backend/db/schema/`. Key tables:

### Core Tables

**Users & Access**

- `users` - Email, password hash, name, role
- `sessions` - Active user sessions with expiration
- `invite_tokens` - Time-limited invitation tokens
- `password_reset_tokens` - Time-limited password reset tokens

**Financial Accounts**

- `card_accounts` - Credit card accounts (issuer, name, last4, billing cycle, credit limit, owner_id)
  - **New table** - Added in Phase 1
  - Links: `owner_id` → `users.id`
  - Every transaction requires a `card_account_id`
- `cards` - Physical/virtual cards (card_account_id, member_id, nickname, last4)
  - **New table** - Added in Phase 1
  - Links: `card_account_id` → `card_accounts.id`, `member_id` → `members.id` (optional)
  - Used for attribution ("who swiped") in shared households
- `pots` - Where money is parked (type, balance, visibility, scope: SOLO/SHARED)
  - ACL enforcement: SOLO (owner-only), SHARED (visibility_acls JSON)
  - Derived values: `reserved_cents`, `available_cents` (calculated, not stored)

**Transactions**

- `merchants` - Where purchases occur
- `tags` - Transaction categories with colors
- `transactions` - Charges and income (merchant, amount, date, **card_account_id** (required), **card_id** (optional))
  - **Breaking Change**: `card_account_id` now REQUIRED (was optional/nullable)
  - **New field**: `card_id` optional for attribution (must belong to same card_account)
  - Links: `card_account_id` → `card_accounts.id`, `card_id` → `cards.id`, `merchant_id` → `merchants.id`
  - Outstanding balance calculated per CardAccount: SUM(amount_cents) per card_account
- `allocations` - How transactions split among members (percentage or fixed)
  - XOR constraint enforced: EITHER `basis_points` OR `amount_cents`, never both
  - Links: `transaction_id` → `transactions.id`, `member_id` → `members.id`

**Reservations & Payments**

- `reservations` - Earmarked funds from pots (pot_id, transaction_id, allocation_id, member_id, amount_cents)
  - Links: `pot_id` → `pots.id`, `transaction_id` → `transactions.id`, `allocation_id` → `allocations.id`, `member_id` → `members.id`
  - Workflow: Transaction created → Reservations earmark funds → Payments settle later
  - Validation: Cannot reserve more than pot balance or allocation amount
- `payments` - Settlement of charges (pot_id, transaction_id, reservation_id, amount_cents, needs_reconciliation)
  - Links: `pot_id` → `pots.id`, `transaction_id` → `transactions.id`, `reservation_id` → `reservations.id` (optional)
  - `needs_reconciliation` auto-flagged when payment ≠ sum(reservations)
  - Reduces CardAccount outstanding balance: SUM(transactions.amount_cents) - SUM(payments.amount_cents)
- `transfers` - Money movement between pots or pot-to-cash

**People**

- `members` - People sharing expenses

**Audit**

- `events` - Activity log (who did what, when)

### Key Schema Rules

**Allocations** enforce one-of:

```sql
CHECK (
  (rule = 'basisPoints' AND basis_points IS NOT NULL AND amount_cents IS NULL) OR
  (rule = 'fixed_amount' AND amount_cents IS NOT NULL AND basis_points IS NULL)
)
```

**Transfers** support cash:

```sql
CHECK (from_pot_id IS NOT NULL OR to_pot_id IS NOT NULL)
-- At least one must be non-null
```

**Outstanding balance** is calculated, not stored:

```sql
-- Computed per CardAccount
SUM(transactions.amount_cents) - SUM(payments.amount_cents)
```

## API Design

### RESTful Endpoints (MVP)

**Authentication**

- `POST /api/auth/login` - Sign in with email/password
- `POST /api/auth/logout` - End session
- `POST /api/auth/invite` - Send invitation email
- `POST /api/auth/accept-invite` - Accept invite and create account
- `POST /api/auth/request-password-reset` - Request password reset
- `POST /api/auth/reset-password` - Complete password reset

**Card Accounts**

- `GET /api/card-accounts` - List card accounts
- `POST /api/card-accounts` - Create card account
- `PATCH /api/card-accounts/:id` - Update card account

**Transactions**

- `GET /api/transactions` - List transactions (filter by CardAccount, unallocated, etc.)
  - **Breaking Change**: All transactions require `card_account_id` (no more nullable)
  - Optional: Filter by `card_account_id` query param for per-account views
- `POST /api/transactions` - Create transaction
  - **Required**: `card_account_id` field must be provided
  - **Optional**: `card_id` field for attribution (must belong to same card_account)
- `GET /api/transactions/:id` - Get transaction detail
- `PATCH /api/transactions/:id` - Update transaction
- `POST /api/transactions/:id/allocations` - Add/update allocations

**Merchants & Tags**

- `GET /api/merchants` - List merchants (autocomplete)
- `POST /api/merchants` - Create merchant
- `GET /api/tags` - List tags
- `POST /api/tags` - Create tag

**Pots**

- `GET /api/pots` - List pots (respects visibility)
- `POST /api/pots` - Create pot
- `PATCH /api/pots/:id` - Update pot
- `POST /api/pots/:id/reserve` - Create reservation

**Payments & Transfers**

- `POST /api/payments` - Record payment from pot to transaction
- `POST /api/transfers` - Transfer between pots or pot-to-cash

**People**

- `GET /api/people` - List members
- `GET /api/people/:id` - Get member detail

**Ledger**

- `GET /api/ledger/balances` - Get per-person balances and net settlement
  - Updated: Now returns per-CardAccount outstanding balances
  - Formula: Outstanding = SUM(transactions.amount_cents) - SUM(payments.amount_cents) per card_account
  - Includes: Pot balances (reserved, available), member allocations, settlement calculations

**Activity**

- `GET /api/events` - List audit events (filterable)

## Key Architectural Decisions

**Why Clean Architecture?**

- Clear separation of concerns
- Testable business logic
- Frontend and backend share domain entities
- Easy to swap infrastructure (database, API framework)

**Why Deno?**

- Built-in TypeScript support
- Modern standard library
- Secure by default
- Single executable for deployment

**Why Drizzle ORM?**

- Type-safe SQL queries
- Lightweight and fast
- Migration support
- Works great with Deno

**Why shared entities?**

- Single source of truth for domain models
- Validation logic shared between frontend and backend
- Reduces duplication and drift
- Type safety across the stack

**Why NOT shared repositories?**

- Backend repositories talk to database (Drizzle)
- Frontend repositories talk to API (fetch)
- Different concerns, different implementations
- Sharing would force unnecessary abstraction

---

This architecture balances simplicity with scalability, keeping the codebase maintainable while supporting the vision of a polished, mobile-first expense management app.
