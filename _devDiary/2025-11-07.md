# Dev Diary Entry - 2025-11-07

## Entity Audit & Pre-MVP Cleanup Spec

Conducted comprehensive audit of existing shared entities against product specifications to identify implementation gaps.

### What We Did

#### **1. Audited All Shared Entities**

Systematically reviewed each entity file in `/shared/entities/` to compare implementation against requirements in:

- `/specs/0. high level.md` (product spec)
- `/specs/1. architecture.md` (technical spec)

Found the shared layer has:

- ✅ 15 entity files implemented
- ❌ 2 critical entities missing (CardAccount, Card)
- ⚠️ 4 entities need refinement (Transaction, Reservation, Payment, Pot)

#### **2. Discovered Critical Gaps**

Used `grep_search` for "CardAccount|Card" across `/shared/entities/*.ts` → **no matches found**

This confirmed the biggest gap: core entities referenced throughout the spec don't exist yet.

**Missing entities**:

- **CardAccount**: Represents credit card accounts (issuer, name, last4, billing cycle, credit limit) - CRITICAL blocker
- **Card**: Optional physical/virtual card attribution within an account - nice-to-have

**Entity refinements needed**:

- **Transaction**: Missing `cardAccountId` (required) and `cardId` (optional) fields
- **Reservation**: Missing `allocationId` and `memberId` to link reservations to specific member allocations
- **Payment**: All fields currently optional (too permissive), should require potId, transactionId, amountCents, paidOn
- **Pot**: Uses `ownerId` (inconsistent with spec language "User")

#### **3. Created Pre-MVP Cleanup Spec**

Created `/specs/000-pre-mvp-cleanup/spec.md` documenting:

- **Missing entities** (CardAccount, Card) with proposed interfaces
- **Entity refinements required** (Transaction, Reservation, Payment, Pot) with specific field additions
- **Validation gaps** organized by entity (Allocation ✅ done, Transaction ⚠️ partial, Payment ❌ missing, Reservation ⚠️ partial, Pot ✅ good)
- **Implementation order** (Phase 1: CardAccount/Card entities, Phase 2: validation, Phase 3: polish)
- **Spec alignment checklist** (CardAccount created, Transaction updated, Payment required fields, Reservation linked to Allocation, exports updated, architecture doc updated, tests added)

### Technical Details

**CardAccount interface (proposed)**:

```typescript
interface CardAccountData extends EntityData {
  name: string; // User-friendly name
  issuer: string; // e.g., "Chase", "Amex"
  last4: string; // Last 4 digits
  billingCycle: number; // Day of month (1-31)
  creditLimitCents?: Cents; // Optional credit limit
  ownerId: string; // User who owns this account
  isActive: boolean; // Soft delete support
}
```

**Business rules**:

- Cannot delete if transactions exist (archive with `isActive: false`)
- If only one CardAccount exists, frontend auto-selects for new transactions
- Outstanding balance calculated per CardAccount: `sum(transactions) - sum(payments)`

**Card interface (proposed)**:

```typescript
interface CardData extends EntityData {
  cardAccountId: string; // Parent CardAccount
  memberId?: string; // Who typically uses this card
  nickname?: string; // e.g., "Alice's card", "Virtual #1"
  last4?: string; // Last 4 of card number
  isActive: boolean; // Soft delete support
}
```

**Business rules**:

- Cards are optional (transactions can exist without Card attribution)
- Cards don't affect splits or payments (attribution only for filtering/reporting)
