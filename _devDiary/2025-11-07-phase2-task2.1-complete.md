**Key Decision**: `needsReconciliation` is NOT in `createSchema` - it's calculated by the service, not provided by callers.

**3. Service Logic**

Implemented reconciliation calculation in PaymentService.createPayment:

```typescript
// Get all reservations for transaction
const reservations = await this.reservationRepo.findByTransactionId(
  validatedData.transactionId
);

let needsReconciliation = false;
if (reservations.length > 0) {
  // Calculate total reserved amount
  const totalReserved = reservations.reduce((sum, r) => sum + r.amountCents, 0);

  // Calculate what total paid will be after this payment
  const totalAfterPayment = totalPaid + validatedData.amountCents;

  // Flag for reconciliation if totals don't match
  if (totalAfterPayment !== totalReserved) {
    needsReconciliation = true;
  }
}
```

**Business Logic**:

- If NO reservations exist → `needsReconciliation = false` (nothing to reconcile against)
- If reservations exist AND total payments match total reservations → `false`
- If reservations exist AND totals differ → `true` (needs reconciliation)

**4. Test Coverage**

**Test Scenarios**:

   - Payment 2: $30.00 (completes total) → `needsReconciliation = false`

### Challenges & Solutions

**Challenge 1**: Deciding when to flag reconciliation

- **Solution**: Flag only when reservations exist AND totals differ
- Rationale: If no reservations, there's nothing to reconcile against

**Challenge 2**: Partial payments handling

- **Solution**: Compare cumulative totals (existing + current payment)
- Each payment is flagged independently based on current state

**Challenge 3**: Database migration naming

- **Solution**: Used simple sequential naming `0000_...`
- Note: Drizzle-kit requires DATABASE_URL, so manual migration created

### Key Learnings

1. **Schema-first approach**: Adding database field first, then entity, then service logic provides clear progression
2. **Calculated fields**: `needsReconciliation` is calculated by service, not provided by API
   - Prevents clients from incorrectly setting the flag
   - Ensures consistency based on actual data state
3. **Business logic placement**: Reconciliation logic belongs in service layer, not entity

   - Requires cross-entity queries (reservations + payments)
   - Service layer has access to repositories

4. **Test scenario design**: Cover positive, negative, and edge cases

   - Positive: Payment matches reservations
   - Negative: Payment differs from reservations
   - Edge: No reservations exist, multiple partial payments

5. **Migration strategy**: Manual migrations work when drizzle-kit has config issues
   - Simple SQL ALTER TABLE statement
   - Can be applied manually or via migration runner
